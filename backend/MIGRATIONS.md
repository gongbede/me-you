# Database Migrations

Me&You uses Alembic to version and apply the PostgreSQL schema. Migration files live in `backend/alembic/versions/`, and Alembic reads the existing `ME_YOU_DATABASE_URL` setting.

Run commands from `backend/` with the environment configured:

```bash
alembic upgrade head
alembic revision --autogenerate -m "describe the schema change"
alembic current
alembic history
alembic downgrade -1
```

Review autogenerated revisions before applying them. The identity schema is in `alembic/versions/0001_initial_schema.py`; Social Core is in `alembic/versions/0002_social_core.py`; Communication Core is in `alembic/versions/0003_communication_core.py`.

Social Core indexing follows current access patterns: posts and comments use author/post plus creation-time indexes for feeds and chronological lists; post likes use a post plus creation-time index; follows add an index for the reverse `following_id` lookup because the composite primary key begins with `follower_id`; notifications use recipient plus creation-time ordering. Composite primary keys prevent duplicate likes/follows, and the database check constraint prevents self-follows.

Posts and comments cascade when their owning user/post is deleted. Notification references to actors, posts, and comments use `SET NULL` so notification history can remain without retaining deleted content; notification recipients cascade with the account.

Communication Core stores `last_read_at` on each conversation membership because read position belongs to a user/conversation pair. Messages are soft-deleted by setting `deleted_at`; normal responses retain safe metadata but omit deleted content. Direct conversations use a sorted pair of user UUIDs in a unique `direct_key`, preventing duplicate two-person conversations at the database level. Message notifications reuse the existing notifications table and add the `MESSAGE` type in revision 0003; no external delivery system is involved.

Education Core is revision `0004_education_core` and contains institutions, faculties, departments, courses, teachers, students, and enrollments. The academic hierarchy cascades from institution to faculty, department, and course. Teacher/student memberships and enrollments use restrictive institution/course/student foreign keys so academic records are not silently destroyed. Teacher and student identity always comes from the authenticated PostgreSQL user; no institution-admin role system exists yet.

Education Learning Core is revision `0005_education_learning_core`. It adds course-teacher assignments, lessons, exercises, assessments, submissions, results, and lesson progress. Results validate their score against the assessment maximum in application logic; course progress is computed from published lesson progress. Learning records use restrictive foreign keys where deleting a parent could destroy academic history.

Alembic is the schema authority. Do not call SQLAlchemy `create_all()` or run migrations automatically from FastAPI startup. MongoDB and the legacy SQLite compatibility layer remain separate from these PostgreSQL migrations.
