# Database Migrations

Me&You uses Alembic to version and apply the PostgreSQL schema. Migration files live in `backend/alembic/versions/`, and Alembic reads the existing `ME_YOU_DATABASE_URL` setting.

Run commands from `backend/` with the environment configured:

```bash
alembic upgrade head
alembic revision --autogenerate -m "describe the schema change"
alembic current
alembic history
alembic downgrade -1
```

Review autogenerated revisions before applying them. The identity schema is in `alembic/versions/0001_initial_schema.py`; Social Core is in `alembic/versions/0002_social_core.py`; Communication Core is in `alembic/versions/0003_communication_core.py`.

Social Core indexing follows current access patterns: posts and comments use author/post plus creation-time indexes for feeds and chronological lists; post likes use a post plus creation-time index; follows add an index for the reverse `following_id` lookup because the composite primary key begins with `follower_id`; notifications use recipient plus creation-time ordering. Composite primary keys prevent duplicate likes/follows, and the database check constraint prevents self-follows.

Downgrading past `0003_communication_core` removes the `MESSAGE` notification type. Revisions `0007_platform_infrastructure` and `0003_communication_core` explicitly refuse that downgrade while `MESSAGE` notifications remain, rather than allowing the later check-constraint recreation to fail or discard rows. Remove or archive those notifications through an approved data-retention procedure before downgrading.

Posts and comments cascade when their owning user/post is deleted. Notification references to actors, posts, and comments use `SET NULL` so notification history can remain without retaining deleted content; notification recipients cascade with the account.

Communication Core stores `last_read_at` on each conversation membership because read position belongs to a user/conversation pair. Messages are soft-deleted by setting `deleted_at`; normal responses retain safe metadata but omit deleted content. Direct conversations use a sorted pair of user UUIDs in a unique `direct_key`, preventing duplicate two-person conversations at the database level. Message notifications reuse the existing notifications table and add the `MESSAGE` type in revision 0003; no external delivery system is involved.

Platform Infrastructure is revision `0007_platform_infrastructure`. Notifications remain recipient-owned and support extensible event types, concise titles, optional structured routing data, unread indexes, and read timestamps. Activity rows are internal domain events, not application or security logs: metadata must contain only bounded, non-sensitive scalar context such as opaque identifiers, event options, and counts. Do not record credentials, contact details, message/post content, grades, or security diagnostics here. Activity targets use opaque type/UUID pairs so domain tables do not depend on the activity store; actor references are nulled when a user is deleted. Activity reads in application services must be scoped to the authenticated actor or protected by the owning domain's authorization checks.

Global Search initially covers institutions and courses only where the authenticated user has an institution membership. It returns safe display fields and uses PostgreSQL-compatible case-insensitive matching; it is not a database-wide discovery mechanism.

Education Core is revision `0004_education_core` and contains institutions, faculties, departments, courses, teachers, students, and enrollments. The academic hierarchy cascades from institution to faculty, department, and course. Teacher/student memberships and enrollments use restrictive institution/course/student foreign keys so academic history is not silently destroyed. Teacher and student identity always comes from the authenticated PostgreSQL user. Institution administration is scoped through `institution_memberships` (revision `0006_institution_memberships`), with `ADMIN`, `TEACHER`, and `STUDENT` roles enforced through centralized authorization helpers.

Education Learning Core is revision `0005_education_learning_core`. It adds course-teacher assignments, lessons, exercises, assessments, submissions, results, and lesson progress. Results validate their score against the assessment maximum in application logic; course progress is computed from published lesson progress. Learning records use restrictive foreign keys where deleting a parent could destroy academic history. Revision `0008_exercise_submissions` adds numbered exercise attempts and teacher feedback, with a unique constraint preventing duplicate attempt numbers for a student/exercise pair. Submission activity and notifications are committed atomically with the attempt or review.

Alembic is the schema authority. Do not call SQLAlchemy `create_all()` or run migrations automatically from FastAPI startup. MongoDB and the legacy SQLite compatibility layer remain separate from these PostgreSQL migrations.

Revisions `0014_privacy_membership_requests`, `0015_education_integrity`, and `0016_account_email_tokens` add privacy defaults and separate pending membership state, PostgreSQL triggers for cross-institution education links/grading maxima, and expiring single-use email action tokens. Revision `0016` stores only SHA-256 token digests and enforces one unconsumed token per user/purpose.
